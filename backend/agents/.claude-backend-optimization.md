This document audits the FastAPI backend (`backend/app/`) and proposes changes
ordered by impact. Each item lists the **problem**, the **fix**, the
**tradeoff**, and an **effort** estimate. File references are clickable.

---

## System summary (what we're optimizing)

- **API**: FastAPI, two routers — [auth.py](../app/api/v1/auth.py) and [songs.py](../app/api/v1/songs.py).
- **Auth**: Spotify OAuth → stateless signed session cookie via `itsdangerous` ([session.py](../app/core/session.py)).
- **Data**: Postgres + `pgvector`, HNSW index on a 1280-dim song embedding ([models.py](../app/db/models.py), [migration](../alembic/versions/d9e1f3a4b205_add_hnsw_index_songs_embedding.py)).
- **ML**: Essentia/TensorFlow EffNet-Discogs for embeddings + genre, `spotdl` for audio download ([spotify_ingest_service.py](../app/services/spotify_ingest_service.py), [audio_genre_classifier.py](../app/services/audio_genre_classifier.py)).
- **Flow**: client polls `/song_recs/` → fetch top tracks from Spotify → download + embed + classify → store → kNN query over candidate songs → dedupe by artist → dispatch 10 recs/day.

# TIER 1 — Quick wins (do now)

## Security

### S1. `SESSION_SECRET` falls back to a hardcoded default — CRITICAL ✅ FIXED (2026-06-10)
- **Resolution**: Removed the default; [session.py](../app/core/session.py) now
  raises `RuntimeError` at import if `SESSION_SECRET` is missing/blank. Added a
  committed [.env.example](../.env.example) and two import-fails-without-secret
  tests in [test_session.py](../tests/test_session.py). Full plan:
  [s1-session-secret-fix-plan.md](s1-session-secret-fix-plan.md).
- **Problem**: [session.py:4](../app/core/session.py#L4) defaults to
  `"dev-secret-change-in-production"`. If the env var is unset in any
  environment, **every session cookie is forgeable** — an attacker can mint a
  valid `session` for any `user_id` and fully impersonate users. The same secret
  also gates rate-limiting: `session_key` ([limiter.py:8](../app/core/limiter.py#L8))
  decodes the cookie to derive the `user:{id}` bucket.
- **Fix**: Fail fast at startup if `SESSION_SECRET` is missing/blank (raise in
  module import or lifespan). No silent default. Generate a strong secret for
  local dev via `.env-backend`.
- **Tradeoff**: Local setup must now define the var (one-time friction). Worth it.
- **Effort**: XS.

### S2. Debug logging leaks session tokens and PII — HIGH ✅ FIXED (2026-06-10)
- **Resolution**: Removed the cookie `print` in
  [dependencies.py](../app/core/dependencies.py) and the
  `traceback.print_exc()` in [auth.py](../app/api/v1/auth.py); the callback error
  print now logs only `type(e).__name__` (no exception message). Kept scope
  minimal — no `logging` module introduced. Added two `capsys` regression tests in
  [test_auth.py](../tests/test_auth.py) asserting tokens/codes/tracebacks never
  reach stdout. Full plan:
  [s2-debug-logging-leak-fix-plan.md](s2-debug-logging-leak-fix-plan.md).
- **Problem**: [dependencies.py:8](../app/core/dependencies.py#L8) prints **all
  cookies on every authenticated request** — including the `session` token.
  Anyone with log access can replay sessions for 30 days. On the OAuth path,
  [auth.py:49](../app/api/v1/auth.py#L49) is **already scrubbed** to
  `type(e).__name__: {e}`; the real leak is the line below it,
  `traceback.print_exc()` ([auth.py:50](../app/api/v1/auth.py#L50)), whose frame
  locals can contain the OAuth `code`/tokens.
- **Audit correction**: the `auth.py:49` print no longer dumps raw stack traces —
  scope this item to removing the `dependencies.py:8` cookie print and the
  `auth.py:50` `traceback.print_exc()`.
- **Fix**: Remove the cookie `print`. Replace ad-hoc prints with the `logging`
  module at appropriate levels; never log raw tokens/cookies. Drop the bare
  `traceback.print_exc()` — the scrubbed `type(e).__name__` + message log is
  enough (use `logger.exception` only at DEBUG if a traceback is needed locally).
- **Tradeoff**: Slightly less verbose local debugging — use a debugger/log level instead.
- **Effort**: XS.

### S3. CORS origin doesn't match the real frontend — MEDIUM (also a bug) ✅ FIXED (2026-06-10)
- **Resolution**: [main.py](../app/main.py) now reads allowed origins from a new
  comma-split `CORS_ALLOWED_ORIGINS` env var (default `https://127.0.0.1:3000`,
  so credentialed requests from the real frontend are accepted), keeps
  `allow_credentials=True`, and tightens to `allow_methods=["GET","POST","OPTIONS"]`
  / `allow_headers=["Content-Type"]` (the methods/headers the frontend actually
  uses). Documented the var in [.env.example](../.env.example) and added
  [test_cors.py](../tests/test_cors.py) asserting the real origin is echoed and
  disallowed/port-less origins are rejected. Full plan:
  [s3-cors-origin-fix-plan.md](s3-cors-origin-fix-plan.md).
- **Problem**: [main.py:41](../app/main.py#L41) allows `https://127.0.0.1`
  (no port) while `FRONTEND_URL` defaults to `https://127.0.0.1:3000`
  ([auth.py:20](../app/api/v1/auth.py#L20)). With `allow_credentials=True`, the
  browser will reject credentialed requests whose origin includes the port, so
  this is both a correctness bug and a config-rot risk.
- **Fix**: Drive allowed origins from an env var (comma-split), include the
  port, and keep `allow_credentials=True`. Avoid `allow_methods=["*"]` /
  `allow_headers=["*"]` when credentials are allowed — list the methods/headers
  actually used.
- **Tradeoff**: One more env var to set per environment.
- **Effort**: XS.

### S4. Explicit/shared timeouts on outbound Spotify calls — LOW ✅ FIXED (2026-06-10)
- **Resolution**: Added a module-level `SPOTIFY_HTTP_TIMEOUT = float(os.getenv(
  "SPOTIFY_HTTP_TIMEOUT", "10.0"))` in
  [spotify_auth_service.py](../app/services/spotify_auth_service.py) and passed it
  to all four `httpx.AsyncClient(timeout=...)` constructions (`exchange_code`,
  `get_top_tracks`, `get_spotify_profile`, `refresh_tokens`). Scoped to **timeouts
  only** — the shared/pooled `AsyncClient` in `lifespan` is deferred (negligible
  connection-reuse win at current traffic; revisit with the scaling items, ties to
  A1). Documented the var in [.env.example](../.env.example) and added
  [test_spotify_timeouts.py](../tests/test_spotify_timeouts.py) asserting the
  configured timeout reaches every outbound call site. Full plan:
  [s4-spotify-timeouts-fix-plan.md](s4-spotify-timeouts-fix-plan.md).
- **Audit correction**: the original premise ("stalls indefinitely / mild DoS")
  is **wrong**. `httpx.AsyncClient()` applies a **default 5s timeout** to all
  operations unless you pass `timeout=None`; none of the clients in
  [spotify_auth_service.py](../app/services/spotify_auth_service.py) disable it,
  so none can hang forever. Demoted MEDIUM → LOW.
- **Problem (revised)**: the implicit 5s is arbitrary and untuned, and each call
  spins up its own `AsyncClient` (no connection reuse).
- **Fix**: Set intentional, per-call timeouts (`timeout=httpx.Timeout(10.0)`) and
  share a single `AsyncClient` created in `lifespan`.
- **Tradeoff**: Need sensible timeout values; too low causes spurious failures.
- **Effort**: XS–S.

### S5. OAuth `state` recorded but never expired — MEDIUM ✅ FIXED (2026-06-10)
- **Resolution**: Added `OAUTH_STATE_TTL_SECONDS = int(os.getenv(
  "OAUTH_STATE_TTL_SECONDS", "600"))` in [auth.py](../app/api/v1/auth.py). Login
  now calls a `_sweep_expired_states` helper before recording a new state (bounds
  memory), and the callback `pop`s the state then rejects it with
  `?error=state_mismatch` if older than the TTL (single-use + TTL'd CSRF). Reused
  the existing `state_mismatch` error (no new frontend copy). Documented the var
  in [.env.example](../.env.example) and added two regression tests in
  [test_auth.py](../tests/test_auth.py) (expired state rejected/consumed; login
  sweeps stale entries). Full plan:
  [s5-oauth-state-ttl-fix-plan.md](s5-oauth-state-ttl-fix-plan.md).
- **Problem**: [auth.py:27](../app/api/v1/auth.py#L27) stores `time.time()` for
  each `state` but the callback never checks age — it only checks existence
  ([auth.py:40](../app/api/v1/auth.py#L40)). Stale states live forever (small
  unbounded memory growth) and the CSRF protection has no TTL.
- **Fix**: Reject states older than ~10 min and sweep expired entries on each
  login. (See A1 for the scaling version.)
- **Tradeoff**: None meaningful.
- **Effort**: XS.

### S6. Missing baseline security headers — LOW/MEDIUM ✅ FIXED (2026-06-10)
- **Resolution**: Added a **pure-ASGI** `SecurityHeadersMiddleware` in
  [main.py](../app/main.py) stamping `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, and
  a locked-down `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`
  onto every response. HSTS (`max-age=31536000; includeSubDomains`) is emitted only
  when `ENABLE_HSTS=true` (default off; enable behind the TLS-terminating nginx).
  Used pure ASGI rather than `@app.middleware("http")` because `BaseHTTPMiddleware`
  drops the body of responses carrying a `BackgroundTask` under Starlette 0.27 (the
  stale-snapshot `/song_recs/` path). Documented `ENABLE_HSTS` in
  [.env.example](../.env.example) and added
  [test_security_headers.py](../tests/test_security_headers.py). Full plan:
  [s6-security-headers-fix-plan.md](s6-security-headers-fix-plan.md).
- **Problem**: No HSTS / `X-Content-Type-Options` / `Referrer-Policy` etc.
- **Fix**: Small middleware adding standard headers. HSTS only behind real TLS.
- **Tradeoff**: None.
- **Effort**: XS.

## Performance

### P1. The TensorFlow model is loaded twice — MEDIUM ⚠️ DEFERRED (2026-06-11)
- **Empirical finding (2026-06-11)**: P1 and P2 are **coupled** — both require
  dropping to the low-level `TensorflowPredict`. An experiment against the real
  graph confirmed `TensorflowPredict(graphFilename=..., outputs=["PartitionedCall:1",
  "PartitionedCall:0"])` returns **both** the embedding and genre heads from a
  single graph load + single TF session, so the fused pass is achievable in
  principle. **But** the hard part is reproducing the preprocessing that
  `TensorflowPredictEffnetDiscogs` does internally:
  - The model input is **not** `TensorflowInputMusiCNN`'s 96 mel-bands — feeding a
    `(n,128,96)` patch tensor triggered a graph reshape error (`6400` vs `81920`
    values), i.e. the expected band count / tensor layout differs (the algorithm's
    own docstring mislabels its preprocessing as MusiCNN).
  - The high-level algo emits **6 patches** for a 7s clip where naive 128-frame /
    62-hop framing yields **5** — its `lastBatchMode=same` / `lastPatchMode` zero-pad
    + trailing-patch handling must be replicated exactly.
- **Why deferred**: Embeddings are **persisted to Postgres** and drive the kNN
  recs, so any drift silently corrupts recommendations for every ingested song.
  There are **no tests and no audio fixtures** for this path, so the audit's
  "byte-for-byte unchanged" bar can't be met cheaply. Moderate benefit on a
  **background ingest** path doesn't justify the validation burden now. **Revisit
  with a committed numerical-equivalence test (synthetic audio, ~0 max-abs-diff
  for both heads) — ideally once ingest moves to a real queue (A2).**
- **Problem**: [spotify_ingest_service.py:29](../app/services/spotify_ingest_service.py#L29)
  loads `TensorflowPredictEffnetDiscogs` (output `PartitionedCall:1`,
  embeddings) and [audio_genre_classifier.py:16](../app/services/audio_genre_classifier.py#L16)
  loads the **same graph file again** (output `PartitionedCall:0`, genre logits).
  Two full copies of the network in memory and doubled startup/warmup cost.
- **Audit correction**: `TensorflowPredictEffnetDiscogs` exposes only a **single
  output tensor** per instance — you can't "read both outputs" from one of these
  objects. Pulling both `PartitionedCall:0` and `:1` from one graph means
  dropping to Essentia's lower-level `TensorflowPredict` (with
  `outputs=["PartitionedCall:0", "PartitionedCall:1"]`) plus replicating the
  EffNet patch-framing that `TensorflowPredictEffnetDiscogs` does for free. That
  is why this is genuinely **M**, not S.
- **Fix**: Load the graph once via `TensorflowPredict` configured for both output
  tensors and run it once per audio; share that single loaded model between the
  embed and classify paths.
- **Tradeoff**: Slightly more coupling between the embed/classify code paths.
- **Effort**: M (revised up from S–M).

### P2. Each track runs the network twice over the same audio — MEDIUM ⚠️ DEFERRED (2026-06-11)
- **Deferred with [P1](#p1-the-tensorflow-model-is-loaded-twice--medium--deferred-2026-06-11)** —
  the single forward pass producing both outputs is the *same* refactor (one
  `TensorflowPredict` call with two output tensors). See P1 for the empirical
  findings and the validation bar required before implementing.
- **Problem**: In [process_top_tracks](../app/services/spotify_ingest_service.py#L140-L162),
  for a new song we call `genre_classifier.classify(audio)` **and**
  `self._embed(audio)` — two independent forward passes over identical 16 kHz
  audio through (effectively) the same EffNet backbone. Inference is the most
  expensive step in ingest. (Scope: the double pass only hits the **new-song**
  branch — existing songs only run `classify` — but new songs are the common case.)
- **Fix**: Single forward pass producing both the embedding and genre logits
  (ties into P1). Roughly halves per-track inference time.
- **Tradeoff**: Couples the two outputs; needs care to keep `None`-genre
  fallback behavior identical.
- **Effort**: M.

### P3. N+1 lazy loads when building dispatch responses — MEDIUM ✅ FIXED (2026-06-11)
- **Resolution**: Added `selectinload` options in
  [spotify_ingest_service.py](../app/services/spotify_ingest_service.py):
  `get_todays_dispatch` eager-loads `UserRecommendation.song → Song.album` (and
  `query_song`); `query_recommendations`'s `base_query` adds
  `selectinload(Song.album)` so the serializer doesn't re-query each candidate's
  album. (Used `selectinload` rather than `contains_eager` because the candidate
  query selects `Album.artist_id` as a column, not the full entity.) Full plan:
  [p3-p4-query-cleanups-fix-plan.md](p3-p4-query-cleanups-fix-plan.md).
- **Problem**: [get_todays_dispatch](../app/services/spotify_ingest_service.py#L288-L300)
  returns `[r.song for r in rows]`, and [SongResponse.from_song](../app/schemas/song.py#L26-L35)
  then touches `song.album` for each — so ~10 recs trigger ~10–20 extra queries
  per dispatch fetch. Same pattern when serializing fresh `query_recommendations`
  results.
- **Fix**: Eager-load with `selectinload(UserRecommendation.song).selectinload(Song.album)`
  (and the `query_song`/`album`). For `query_recommendations`, the
  `db.query(Song, Album.artist_id)` already joins Album — also load
  `Song.album` so the serializer doesn't re-query.
- **Tradeoff**: None real; one tuned query beats N small ones.
- **Effort**: S.

- **Effort**: S.

### P5. Tune pgvector HNSW recall/speed — LOW/MEDIUM — ✅ P5a DONE / 🚧 P5b PARTIAL — index rebuild blocked (2026-06-15)
- **Measured (read-only, live RDS, 110,833 candidates)**: default `ef_search=40` <
  over-fetch `pool_size=50`, so the fallback kNN returned only **39 of 50** rows
  (shrinking the artist-dedupe pool — a rec-quality bug). The genre branch (filter
  on the *joined* `albums.genre`) ignores the HNSW index and **seq-scans all 110k**.
  Cranking `ef_search` high backfires (200 → genre branch post-filtered to 9 rows).
  Full plan + numbers: [p5-hnsw-tuning-fix-plan.md](p5-hnsw-tuning-fix-plan.md).
- **✅ P5a — Resolution (2026-06-12)**: `query_recommendations` now scopes
  `hnsw.ef_search` to `2*pool_size` per transaction via
  `SELECT set_config('hnsw.ef_search', :ef, true)` before the pool queries
  ([spotify_ingest_service.py](../app/services/spotify_ingest_service.py#L228)).
  Verified read-only: fallback **39 → 50**. Capped at 2× intentionally (higher
  flips the genre branch to the collapsing index plan).
- **🛠️ P5b — In progress (agent-reviewed plan)**: the genre branch can't use the
  index because the filter is on a *joined* table; pgvector iterative scan only
  helps same-table filters. Fix = denormalize `albums.genre` → `songs.genre` (NULL
  for all candidates today) + backfill + sync trigger (the candidate scraper is
  **external to this repo**) + filter `Song.genre` + `hnsw.iterative_scan=
  'relaxed_order'`. A btree on `albums.genre`/`is_candidate` would **not** help (the
  vector sort dominates, not the join). Detailed, agent-reviewed + DB-measured plan
  with a **drop-index → backfill → rebuild** rollout (corrected cost model: `songs`
  heap is only **23 MB** — the 1280-dim embeddings are stored **EXTERNAL/TOAST** and
  are *not* rewritten by a genre-only UPDATE; the real cost is HNSW index churn, so
  drop the index, backfill ~110k candidates, rebuild clean; gated on an `EXPLAIN`
  showing the index engages before any trigger/code change):
  [p5b-genre-denormalization-plan.md](p5b-genre-denormalization-plan.md).
- **🚧 P5b — Partial (2026-06-15)**: genre **backfill is DONE + committed** on live
  RDS (all 110,833 candidates; ran in 4.7s with the index dropped). **But the HNSW
  index rebuild is the blocker** — the ~1 GB RDS instance can't bulk-build it: full
  vector spills the graph and collapses to ~0.18 tuples/sec (~3-day ETA); a halfvec
  build (~284 MB graph, fits) ran steady ~21–37 tuples/sec but a laptop network/DNS
  blip severed the ~1 hr connection mid-build. **The index is currently DROPPED**
  (both branches seq-scan — correct, slower; OK pre-launch). Remaining: rebuild the
  index (halfvec HNSW) **from a stable host w/ TCP keepalives**, apply migration
  [f6a2b3c4d5e6](../alembic/versions/f6a2b3c4d5e6_denormalize_song_genre.py) to install
  the sync trigger, and land the `query_recommendations` filter/iterative-scan/halfvec-
  cast change. Full execution log + resume steps: §6–§7 of
  [p5b-genre-denormalization-plan.md](p5b-genre-denormalization-plan.md).
- **Effort**: P5a XS (done) / P5b M (schema done; index rebuild gated on a stable
  build host, not on this 1 GB instance from a laptop).

### P6. Drop `create_all` at startup; rely on Alembic — LOW ⚠️ DEFERRED — premise broken (2026-06-11)
- **Audit correction**: the "just remove `create_all`" fix is **unsafe as
  written**. **No migration in [alembic/versions](../alembic/versions/) runs
  `op.create_table` for the core tables** — the root migration
  [ad1aecf9f82f](../alembic/versions/ad1aecf9f82f_initial_schema.py#L21) only
  `add_column`s onto an already-existing `user_top_songs`. The six base tables
  (`users`, `artists`, `albums`, `songs`, `user_top_songs`,
  `user_recommendations`) are created **solely** by `create_all`; on a fresh DB
  `alembic upgrade head` would fail with `relation "user_top_songs" does not
  exist`, and the [Dockerfile](../Dockerfile) has **no** `alembic upgrade` step.
  So `create_all` is currently load-bearing for bootstrap. **Re-scoped: effort is
  M, not XS.**
- **Problem**: [main.py](../app/main.py) runs `Base.metadata.create_all` on boot.
  It can't create the HNSW index or run migrations, so it diverges from the real
  schema and masks migration drift.
- **Fix (revised)**: First author a baseline `op.create_table` migration for all
  six tables (the new root the existing migrations chain onto), add an
  `alembic upgrade head` step to deploy, and `alembic stamp` the
  already-deployed DB so its history stays consistent — *then* remove
  `create_all`.
- **Tradeoff**: Baseline migration must exactly match the live schema; touches
  migration history on a deployed DB. Do it deliberately, not as a quick win.
- **Effort**: M (was mislabeled XS).

# TIER 2 — Architectural (review later, not now)

### A1. Externalize in-memory state before scaling horizontally — BLOCKS SCALING
- **What**: `oauth_states` and `processing_users` live in `app.state`
  ([main.py:25-26](../app/main.py#L25-L26)), and the `slowapi` limiter uses the
  default in-memory storage ([limiter.py:20](../app/core/limiter.py#L20)). With
  >1 worker or >1 replica: OAuth callbacks land on a worker that never saw the
  `state` (spurious `state_mismatch`), the per-user "processing" guard and
  daily-limit serialization stop working across workers, and rate-limit counters
  fragment.
- **Audit correction**: there is **no shared `AsyncClient` in `app.state`** —
  each Spotify call constructs its own (the shared client is only a *proposal*
  in S4, not current state). `app.state` holds `ingest_service`, `oauth_states`,
  and `processing_users`.
- **Why deferred**: Correct as-is on a single process. This is the **top item to
  resolve the moment you add a second worker/replica.**
- **Direction**: Move `oauth_states` and `processing_users` to Redis (or a small
  Postgres table); point `slowapi` at a shared Redis storage backend.

### A2. Move heavy ingest off FastAPI `BackgroundTasks` to a real queue
- **What**: `_run_process_top_tracks` ([songs.py:17-32](../app/api/v1/songs.py#L17))
  runs `spotdl` downloads + TensorFlow inference inside the web process via
  `BackgroundTasks`. CPU-bound TF work and subprocess I/O block/compete with the
  serving process; failures aren't retried or observable; work dies on deploy/restart.
- **Direction**: Offload to Celery/RQ/arq workers (separate process/box, GPU
  optional). The API enqueues a job and the existing `/status` poll reads job
  state. This also unblocks A1's `processing_users` (job state becomes the
  source of truth).

### A3. `async def` routes doing synchronous DB work block the event loop
- **What**: [get_recs](../app/api/v1/songs.py#L60) is `async` but calls
  blocking psycopg2 queries (e.g. `with_for_update().one()`) directly on the
  event loop. Under load this serializes unrelated requests.
- **Direction**: Either make the DB-touching routes plain `def` (FastAPI runs
  them in a threadpool) or adopt async SQLAlchemy + asyncpg. Pick one convention.

### A4. Encrypt Spotify tokens at rest
- **What**: `spotify_access_token` / `spotify_refresh_token` are stored in
  plaintext ([models.py:24-25](../app/db/models.py#L24-L25)). A DB compromise
  hands an attacker durable access to every user's Spotify account.
- **Direction**: Encrypt with an app-held key (e.g. Fernet) or use Postgres
  `pgcrypto`. Pre-launch is the cheapest time to introduce the column format.

### A5. Concurrent-download collision in the shared downloads dir
- **What**: `_download` diffs `DOWNLOADS_DIR.rglob("*")` before/after a `spotdl`
  run to find the new file ([spotify_ingest_service.py:44-60](../app/services/spotify_ingest_service.py#L44)).
  Two simultaneous ingests (different users) share one directory and can pick up
  each other's files; the rglob also slows as the dir grows.
- **Direction**: Per-job temp dir (`tempfile.mkdtemp`) passed as `--output`, torn
  down in `finally`. Naturally correct once A2's queue isolates jobs.

### A6. Unnecessary re-ingest churn when all top tracks have been used as query
- **What**: [snapshot_is_stale](../app/services/spotify_ingest_service.py#L186-L197)
  returns stale once `all_queried`, triggering a fresh Spotify top-tracks fetch
  and a full `UserTopSong` rebuild just to refill query candidates.
- **Audit correction**: "re-downloads and re-embeds from scratch — expensive" is
  **overstated**. `add_user_top_songs` reuses any existing `Song` by
  `spotify_track_id` and copies its genre
  ([:101](../app/services/spotify_ingest_service.py#L101)), and
  `process_top_tracks` fast-paths songs that already carry a genre
  ([:126](../app/services/spotify_ingest_service.py#L126)) — so it rarely
  re-downloads/re-embeds. The real waste is an unnecessary Spotify call plus row
  churn (DELETE + re-insert) on every cycle. Severity: minor.
- **Direction**: When the snapshot is unchanged, reset `used_as_query=False`
  (cycle existing candidates) instead of rebuilding; only re-fetch when the
  Spotify snapshot actually changed.

### A7. Stateless logout can't revoke a leaked session
- **What**: `itsdangerous` tokens are valid for 30 days regardless of logout
  ([auth.py:71-76](../app/api/v1/auth.py#L71)); logout only clears the client cookie.
- **Direction**: If revocation matters, add a server-side session/version check
  (e.g. a `session_version` on `User` baked into the token). Tradeoff: gives up
  pure statelessness for a DB read per request.
